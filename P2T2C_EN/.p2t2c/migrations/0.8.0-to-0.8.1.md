# Migration 0.8.0 to 0.8.1

## Summary

This migration removes the ambiguity of the `CP` abbreviation. Previously `CP` referred to both Change Proposal (the human-submitted proposal) and Change Pack (the AI-generated candidate pack), which caused confusion. The naming is now:

- `SP` = Submit Proposal (the human-submitted proposal).
- `CPK` = Change Pack (the AI-generated candidate pack).

The two no longer share the `CP` abbreviation. This is a naming convention change only; no workflow semantics or gate logic change.

## What Changed

| Area | Change |
|---|---|
| `docs/change_proposals/` → `docs/submit_proposals/` | Proposal directory renamed. |
| `docs/submit_proposals/CP_TEMPLATE.md` → `docs/submit_proposals/SP_TEMPLATE.md` | Proposal template renamed. |
| Proposal instance naming `CP-YYYYMMDD-*.md` → `SP-YYYYMMDD-*.md` | New proposals use the SP prefix. |
| `.p2t2c/templates/change_pack/` → `.p2t2c/templates/change_packs/` | Change Pack template directory renamed. |
| `docs/sot/governance/P2T2C_GOVERNANCE.md` | Stage table labels Change Pack with the `CPK` abbreviation; stage prose refers to proposals as `SP`. |
| `P2T2C_AGENTS.md`, `P2T2C_README.md` | Abbreviation convention note added; directory and workflow references updated to the new names. |
| `.p2t2c/ownership.yaml`, `docs/sot/manifest.yaml` | Managed paths and `proposal_root` updated to `docs/submit_proposals`, `SP-*.md`. |
| `.p2t2c/bin/check_p2t2c.sh`, `p2t2c_install.sh`, `p2t2c_upgrade.sh` | Paths, globs, and error messages updated to SP/CPK naming. Assert version `0.8.1`. |
| `.p2t2c/VERSION`, `.p2t2c/manifest.yaml` | Version `0.8.1`. |

## Upgrade Rules

- This is a naming convention change only; workflow semantics, gates, and stop-the-line conditions are unchanged.
- The upgrade script marks the old managed template files obsolete and removes them, only when those files were not locally modified since the last lock.
- Project-owned historical proposal instances (old `docs/change_proposals/CP-*.md`) are not auto-migrated or renamed and remain valid historical records. To unify naming, you may manually move them to `docs/submit_proposals/` and adopt the `SP-` prefix after the upgrade.
- Proposals created after the upgrade must live in `docs/submit_proposals/` and use `SP-YYYYMMDD-...` naming.
