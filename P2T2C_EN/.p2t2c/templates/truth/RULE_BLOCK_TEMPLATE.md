# Rule Block Template

Truth rules are recorded in two layers to reduce the AI's per-task reading volume (see RULE-GOV-012):

- **Active layer**: written in the main SoT file under `docs/sot/**`, keeping only execution-time fields.
- **History layer**: lifecycle metadata (`Source`, `Supersedes`, `Superseded by`, `Migration required`, downstream projections) and any `Superseded`/`Deprecated` rule in full, written in a sibling `*_HISTORY.md`. `make check` combines both layers for integrity checks; the AI reads only the Active layer by default.

---

## Active-layer Rule Block (written into the main SoT file)

```text
### RULE-{AREA}-{NNN}: {Rule title}

Status: Active
Phases: {one or more phase tokens, comma-separated; see Allowed phases below}

Rule:

{One clear, executable, verifiable rule.}

Validation:

- {automated test / manual acceptance / governance check / code review checklist}

Stop-the-line if:

- {when AI must pause for human confirmation}
```

Allowed phases (stable tokens, matching the manifest `phases` list):

- `bootstrap` — initialize repository
- `change_pack` — generate Change Pack
- `apply_change_pack` — apply Change Pack / Truth Patch
- `execution_pack` — generate Execution Pack (spec/plan/tasks)
- `single_task` — execute a single task
- `acceptance` — acceptance and closure
- `install_upgrade` — install and upgrade
- `all` — workflow-root rules spanning every phase (e.g. the single path, Truth boundaries)

`Phases` must contain at least one token. In a given phase the AI reads only the rules whose `Phases` includes that phase (or `all`). A new rule only needs to declare its phases; the per-phase reading list is generated by `check_p2t2c.sh` and is not hand-maintained.

---

## History-layer entry (written into `*_HISTORY.md`)

Each Active rule has a corresponding lifecycle record in the History file; the full text of any superseded rule lives only in the History file.

```text
### RULE-{AREA}-{NNN}

Status: Active | Superseded | Deprecated
Source: {SP / ADR / human decision}
Supersedes: {RULE-ID or None}
Superseded by: {RULE-ID or None}
Migration required: Yes / No
Rationale: {Why this rule exists.}
Downstream projections:
- Spec: {which specs should cite this}
- Tests: {which tests should cover this}
- Code: {which modules should implement this}
```

Constraints (verified by RULE-GOV-009, scanning the Active + History combination):

- The `RULE-{AREA}-{NNN}` identifier is unique across all of `docs/sot/**` (including History).
- The lifecycle chain is bidirectional: `RULE-A` with `Superseded by: RULE-B` must match `RULE-B` with `Supersedes: RULE-A`.
- Every identifier named in `Supersedes`/`Superseded by` must resolve to a real entry in `docs/sot/**`.
- A rule named by any `Superseded by` field must not retain `Status: Active`.

Code anchor (RULE-GOV-010):

- Implementing code carries a pointer-only comment such as `Implements: RULE-{AREA}-{NNN}`.
- The anchor records the pointer only; the rule text stays in SoT, never in the code comment.
